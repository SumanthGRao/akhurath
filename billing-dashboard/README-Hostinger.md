# Hostinger PHP deployment

The main Akhurath site is PHP/Apache hosted. For the website URL `/billing-dashboard/`, use the PHP entry point in this directory. The standalone Node app remains available for environments that can run Node, but pushing it alone does not start a Node process on the PHP website.

## Deploy

1. Push the repository changes and confirm the Hostinger Git deployment has updated the website files.
2. Confirm the live site has `billing-dashboard/index.php`, `billing-dashboard/api.php`, `billing-dashboard/invoice-download.php`, `billing-dashboard/public/`, and the existing root `includes/` files.
3. Confirm the site's existing `includes/config.php` or `config/database.local.php` connects PHP to the MariaDB database.
4. Select the site database in phpMyAdmin and run `billing-dashboard/sql/001_php_hostinger.sql` for a new billing installation.
5. For an existing billing table created before invoice linking, run `billing-dashboard/sql/003_link_invoices.sql` once. Then run `billing-dashboard/sql/005_billing_groups.sql` once to enable automatic folder grouping and accountant group/split controls. Skip both migrations on a fresh installation made from the updated `001_php_hostinger.sql`, which already includes these columns. The Access page attempts the additive accountant-role migration automatically. If the site database user cannot alter `users.role`, run `billing-dashboard/sql/002_php_hosting_accountant_role.sql` once in phpMyAdmin.
   If an invoice or payment action says its audit entry could not be saved, run `billing-dashboard/sql/004_billing_audit_log.sql` in phpMyAdmin and confirm the site database user has `INSERT` permission on `billing_audit_log`.
6. Open `/admin/dashboard-access.php` as an administrator and use the **Accountant billing dashboard** section to create or remove accountant logins. Existing administrators can also sign in. Accounts created before the role migration may appear under **Accounts needing a role**; explicitly choose **Make accountant** for the intended account to preserve its existing password hash.
7. Apply `billing-dashboard/sql/006_upi_payment_claims.sql` after the studio invoice tables exist. This adds tokenized public payment links, claim records, and the `payment_claimed` state. The migration is safe to rerun.
8. Install the local SVG QR package from `billing-dashboard/composer.json` with Composer in a PHP 8.1+ build environment, commit its generated `composer.lock`, and upload `billing-dashboard/vendor/` to Hostinger alongside the PHP files. The QR is generated locally; do not substitute a third-party QR URL.
9. Set `AKH_BILLING_N8N_TOKEN` as a server environment secret or define it in the untracked `includes/config.php`. Never add its value to Git.
10. In the live Hostinger PHP config, verify `AKH_PUBLIC_PAYMENT_BASE_URL`, `AKH_STUDIO_UPI_ID`, and `AKH_STUDIO_UPI_PAYEE_NAME`, and set a unique `AKH_PUBLIC_PAYMENT_TOKEN_SECRET` of at least 32 random characters. Never commit the token secret. Keep the page in setup-required mode until the UPI ID and payee name have been independently checked against the receiving bank account. See [upi-payment-workflow.md](docs/upi-payment-workflow.md) for the n8n/WhatsApp branch and staged test plan.
11. Re-test `https://akhurathstudio.com/billing-dashboard/` and the login, invoice, claim, verification, and clearance flows using staging data before enabling the live WhatsApp node.

The accountant invoice builder is restricted to the billing delivery flow. It reuses the studio invoice generator for tax, PDF previews/downloads and email, and updates the billing row only after the invoice email succeeds or an accountant records the manual send reference. The accountant role does not receive access to the full admin invoice-management screen.

Pending deliveries are automatically suggested as one invoice group when they share a non-empty `folder_id`, customer name, and phone. Accountants can select pending projects to manually group them or split selected projects into single-project invoices before creating an invoice. Combined invoices contain one editable line per project. All delivery rows linked to the same invoice are marked cleared together when that invoice's payment is recorded; n8n still processes and delivers each final file separately after clearance.

When an accountant confirms that an invoice was sent manually, the builder POSTs a `billing.invoice.sent_manual` JSON event to n8n. Emailing the invoice emits `billing.invoice.sent` after success. For combined invoices both events include the `deliveries` array. When payment setup is configured, the payload includes a stable public `payment_url`, `payment_url_suffix`, and token-protected `invoice_pdf_url` for a sent invoice. The existing PDF preview remains accountant-protected; the public download route only serves the linked sent invoice and never the final video. Configure the n8n Webhook Header Auth name `X-Webhook-Secret` and matching private secret. n8n must route invoice-sent events to an approved WhatsApp document template, require all payment/PDF URL fields, and deduplicate `event_id` in `billing_webhook_events`. Payment claims emit `billing.invoice.payment_claimed`; claims are unverified and never trigger delivery. Exact template and node mapping are in [upi-payment-workflow.md](docs/upi-payment-workflow.md).

After an accountant confirms the incoming bank credit, `api.php?action=clear-{id}` commits the payment clearance and then sends one `billing.payment.cleared` POST to the separate n8n delivery webhook. Combined invoices include one `deliveries` entry per project. The webhook URL defaults to the production URL supplied for the delivery workflow and can be overridden with `AKH_N8N_DELIVERY_WEBHOOK_URL`; the separate `AKH_N8N_DELIVERY_WEBHOOK_SECRET` must be set in the untracked live `includes/config.php` or the server environment. n8n must use POST and Header Auth (`X-Webhook-Secret`) and deduplicate using `event_id`. A failed notification does not undo confirmed payment; the API response flags it so the accountant can check n8n instead of clearing again.

The PHP adapter uses the parent site's session, PDO connection and CSRF helper. Accountant sessions are isolated from administrator sessions and only accept the `accountant` role; removing an account revokes its next API request. It does not need npm on Hostinger. Until the billing table is imported, the page loads but the API reports a database configuration/schema message; no live database is claimed to be connected by this commit.

The separate n8n workflow must use `Authorization: Bearer <AKH_BILLING_N8N_TOKEN>` with `api.php?action=n8n-eligible`, `api.php?action=n8n-claim-{id}`, and `api.php?action=n8n-complete-{id}`. Before changing Drive permissions, n8n must re-check that the exact claim still has a sent invoice and cleared payment. Do not use public `anyone` Drive sharing.
